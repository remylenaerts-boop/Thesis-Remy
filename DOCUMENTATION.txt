CHAPTER 1 — WHAT THIS SYSTEM DOES (Big Picture)
================================================================================

Overview
--------
This system is a proof-of-concept AR (Augmented Reality) assistant for MIG/MAG
welding. A welder wearing a pair of AR glasses receives live feedback about their
welding process without having to look away from the work. The glasses show:

  - Live electrical readings: current (amperage), voltage, and shielding gas flow
  - The position of the weld pool, overlaid on the live camera image
  - A history bar showing porosity risk over the last 30 seconds

The goal is to help a welder maintain correct parameters without stopping to read
gauges, and to learn from the visual overlay where their technique drifts.

The AR glasses used are Epson Moverio BT-300 — a commercial Android-based
heads-up display with a see-through screen. The welder can see both the real
world and the digital overlay simultaneously.

System Components at a Glance
------------------------------
  1. Python AI program     — reads welding parameters from sensor hardware,
                             runs on a laptop/PC connected to the welder.
                             Exposes the data at http://127.0.0.1:8060

  2. Java Spring Boot server (THIS CODEBASE)
                           — the central hub. Receives data from Python,
                             decides what to forward and when, serves the
                             dashboard, and keeps the glasses connected.
                             Runs at http://localhost:9999

  3. Epson BT-300 glasses  — Android device. Connects to the server over Wi-Fi,
                             displays live welding data and detection overlays.

  4. OpenCV pool detector  — Python script (pool_detector.py) that watches the
                             camera feed for the bright glow of the weld pool and
                             reports its position back to the server.

  5. Web dashboard         — a browser page at http://localhost:9999/dashboard
                             where the operator controls everything: enables/disables
                             data streaming, the camera, and pool tracking; adjusts
                             detection settings; and reviews recorded sessions.

Data Flow
---------
  Python AI  →  Java server  →  AR glasses (SSE stream)
                    ↑
              Dashboard (browser)

  Glasses camera  →  Java server  →  Pool detector (file system)
                          ↓
                     Java server  →  AR glasses (SSE pooldetection event)

CHAPTER 2 — ARCHITECTURE OVERVIEW
================================================================================

Why a Central Server?
---------------------
The AR glasses are a constrained Android device — they are not powerful enough to
run an AI model or a full sensor pipeline. The laptop/PC connected to the welder
does the heavy computation, and the server acts as the translation layer between
that computation and the glasses.

A central server also makes it easy to add new clients (a tablet for a supervisor,
a recording system, a second pair of glasses) without changing any of the existing
programs. Each new client simply connects to the same SSE stream.

Package Structure
-----------------
The Java code is split into two packages:

  com.example.thesisremy.controller
    - ControllerClass.java    — the main SSE stream, pool detection intake
    - DashboardController.java — dashboard page and all /api/* endpoints

  com.example.thesisremy.serviceandcomponents
    - ServerState.java        — single source of truth for all runtime flags
    - Broadcast.java          — manages SSE connections and pushes data
    - DataGetter.java         — polls Python AI every second
    - FrameWebSocketHandler   — receives camera frames over WebSocket
    - DnsConfig.java          — mDNS registration so glasses find the server by name
    - WebSocketConfig.java    — WebSocket endpoint configuration
    - StartupLogger.java      — prints startup summary to the console

  ThesisRemyApplication.java  — Spring Boot entry point

CHAPTER 3 — TECHNOLOGY CHOICES AND WHY
================================================================================

Why Spring Boot (Java)?
-----------------------
Spring Boot is a mature framework for building HTTP servers in Java. It handles
the low-level networking, thread management, and request routing automatically,
letting the code focus on the business logic rather than socket management.

For this thesis the key reasons were:
  - Built-in SSE support via SseEmitter — no extra libraries needed
  - Built-in WebSocket support via BinaryWebSocketHandler
  - The @Scheduled annotation makes polling loops trivial to set up
  - Graduates of the faculty will recognize it if they continue this work

Why SSE (Server-Sent Events) instead of WebSocket for data?
------------------------------------------------------------
Both SSE and WebSocket provide a persistent connection between server and client.
The difference is direction:

  WebSocket = two-way (server and client can both send at any time)
  SSE       = one-way  (server sends, client only listens)

For delivering welding data to the glasses, one-way is exactly what we need —
the glasses are consumers of data, not producers. SSE is simpler, works over
plain HTTP (no upgrade handshake), and reconnects automatically if the connection
drops. SSE is natively supported in Android via OkHttp's EventSource library.

WebSocket IS used for the camera feed in the other direction (glasses → server),
because there the glasses are the producers (sending binary JPEG frames) and SSE
does not support client-to-server binary data.

Why Named SSE Events?
---------------------
SSE supports named events — a client can subscribe to specific event types and
ignore others. This system uses three named events on a single connection:

  "welddata"      — welding parameters from the Python AI
  "pooldetection" — weld pool coordinates from the OpenCV detector
  "cameraControl" — server command to start or stop the camera

Using a single connection with named events means the glasses do not need to
manage multiple connections. Each data type is cleanly separated on the same
channel. Android's EventSource API supports per-name listeners natively.

Why mDNS for Service Discovery?
--------------------------------
The server runs on a laptop that gets a different IP address from the Wi-Fi router
every time it connects (DHCP). If the glasses app had the IP address hardcoded,
it would break every session.

mDNS (multicast DNS) solves this by letting the server announce itself by a fixed
human-readable name ("sse-server.local") on the local network. The glasses always
connect to that name, and the DNS resolution figures out the current IP address
automatically — the same way your laptop finds the printer without knowing its IP.

The JmDNS library (Java Multicast DNS) handles the announcement.
Note: on Windows, the Windows Firewall must allow inbound UDP on port 5353 for
mDNS to function. This is the only manual setup step on the server machine.

Why Python for the AI and Pool Detector?
-----------------------------------------
The AI model that reads sensor values was pre-existing when this project started.
It was already written in Python, exposing its data at http://127.0.0.1:8060.
Python is also the natural home for OpenCV — the standard computer vision library
used for the pool detector — because OpenCV has the most complete Python bindings.

The Java server and Python scripts communicate over localhost HTTP: clean, simple,
and language-agnostic. If the AI is ever rewritten in another language, the
interface remains the same.

Why OpenCV for Pool Detection?
-------------------------------
OpenCV (Open Source Computer Vision Library) is the industry standard for image
processing tasks like this. The weld pool detection is a brightness-based blob
detector — the weld pool (and the flashlight stand-in used in testing) is the
brightest region in the frame. OpenCV provides all the needed operations
(Gaussian blur, thresholding, morphological operations, contour finding) as
efficient, well-tested C++ functions callable from Python.

Why ffmpeg for Video Recording?
--------------------------------
The camera feed arrives as individual JPEG frames. Storing them individually would
produce thousands of small files and be difficult to review. ffmpeg stitches a
numbered sequence of JPEG files into an MP4 video with a single command. ffmpeg
is the standard tool for this on every platform, handles codec selection
automatically, and produces a video that plays in any browser or media player.

CHAPTER 4 — SERVER STATE (ServerState.java)
================================================================================

The Problem: Shared Mutable State
-----------------------------------
The server runs multiple things at the same time:
  - The HTTP request handler thread serves the dashboard and API
  - The @Scheduled DataGetter thread polls Python every second
  - The SSE broadcaster pushes data to the glasses
  - The WebSocket handler receives camera frames

These threads all need to read and change the same flags (is polling enabled?
is the camera on?). In Java, sharing data between threads without care leads to
race conditions — where two threads read or write at the same time and produce
unpredictable results.

The Solution: volatile
-----------------------
All fields in ServerState are marked `volatile`. In Java, `volatile` guarantees
that when one thread writes a new value, every other thread immediately sees the
updated value. Without volatile, a thread might cache the old value and never
notice the change.

Fields and Their Purpose
-------------------------
Runtime toggles (all start as false — must be enabled from the dashboard):
  pollingEnabled   — when false, DataGetter stops asking Python for data entirely
  streamingEnabled — when false, data is fetched and deduplicated but not sent to glasses
  cameraEnabled    — when false, incoming camera frames are discarded and the glasses
                     are told to stop their camera (via a "cameraControl" SSE event)
  trackingEnabled  — when false, pool detection results are accepted but not forwarded

Detector settings (read by pool_detector.py via GET /api/settings):
  brightnessThreshold — pixels brighter than this value are treated as the weld pool
  blurKernel          — Gaussian blur radius before thresholding
  morphKernel         — morphological erosion/dilation kernel size
  minBlobArea         — minimum blob area; smaller blobs are noise
  minCircularity      — blobs less round than this are rejected
  videoFramerate      — fps for the stitched MP4 recording

Android app settings (fetched by the app on launch via GET /api/app-settings):
  voltageMin/Max, amperageMin/Max, gasFlowMin/Max
                      — gauge display ranges on the AR overlay
  showPoolDetection   — whether to draw the detection circle on the glasses screen
  overlayOpacity      — transparency of the AR overlay (0.0 = invisible, 1.0 = opaque)
  heatbarDuration     — how many seconds of porosity history the heatbar shows

Design Decision: Why lastDataPacket is initialized to "" not null
------------------------------------------------------------------
Java's Map.of() does not allow null values — passing null throws a
NullPointerException at runtime, not at compile time. When lastDataPacket was
null (before a first poll), the /api/status endpoint crashed with HTTP 500 on
every 2-second dashboard refresh. This silently broke the toggle buttons because
JavaScript was receiving 500 errors instead of the JSON with button states.

The fix: initialize lastDataPacket to an empty string "". The dashboard JavaScript
guards against empty strings with `if (!raw) return;`, so it ignores the empty
value gracefully.

CHAPTER 5 — SSE BROADCAST (Broadcast.java)
================================================================================

What It Does
------------
Broadcast is the post office of the server. When data arrives from Python or from
the pool detector, Broadcast delivers it to every connected AR glasses device.

Each connection is represented by a Spring SseEmitter object. Broadcast holds all
active emitters in a list and loops through them when new data arrives.

Thread Safety: CopyOnWriteArrayList
-------------------------------------
The list of emitters uses CopyOnWriteArrayList instead of a regular ArrayList.
The reason: a new glasses device can connect (adding to the list) at the same
moment that a broadcast is looping through the list. With a regular ArrayList,
this would cause a ConcurrentModificationException and crash the broadcast.

CopyOnWriteArrayList handles concurrent access by making a fresh copy of the
internal array on every write. Reads (loops) never see a partially-modified list.
The trade-off is that writes are slightly more expensive — acceptable here because
connections are infrequent and broadcasts are the frequent operation.

Ghost Connection Problem and Heartbeat Solution
------------------------------------------------
When a Wi-Fi connection drops abruptly (glasses moved out of range, network hiccup),
Spring does not always detect the dead connection immediately. The emitter stays in
the list even though the glasses are gone. If the glasses then reconnect, the old
dead emitter is still there alongside the new one.

The heartbeat is the fix: every 30 seconds a scheduled method sends a small SSE
comment (a line starting with ':') to every emitter. Comments carry no data and
are ignored by the client. But they cause an IOException on any connection that has
silently died — and on IOException, the dead emitter is removed from the list.

This means that at worst, a ghost connection persists for up to 30 seconds after
a crash. In practice, the next broadcast attempt also throws IOException and clears
it immediately.

Named vs Unnamed Events
-----------------------
broadcast()       — sends data as an unnamed SSE event. The Android EventSource
                    listener receives it in onMessage(). Used for weld data.
                    Unchanged from the original app so no Android changes are needed.

broadcastNamed()  — sends data with an explicit event name. The Android app can
                    register a listener for a specific name. Used for:
                    "pooldetection" — weld pool coordinates
                    "cameraControl" — camera on/off command

CHAPTER 6 — DATA GETTER (DataGetter.java)
================================================================================

What It Does
------------
DataGetter is the bridge between the Python AI and the glasses. Once per second,
it asks Python "what are the latest welding readings?" and, if the answer has
changed, forwards the new data to all connected glasses.

The @Scheduled Annotation
--------------------------
`@Scheduled(fixedRate = 1000)` tells Spring to call pollAndBroadcast() every
1000 milliseconds (1 second). This requires @EnableScheduling on the main
application class. Without that annotation, @Scheduled methods are ignored silently.

Three Layers of Safety
-----------------------
  1. Polling toggle: if pollingEnabled is false, the method returns immediately
     without contacting Python. Used when the operator has not yet enabled the system.

  2. Deduplication: if the JSON response from Python is identical to the last
     response, nothing is sent. This avoids flooding the glasses with duplicate
     packets when a weld is in progress and parameters are stable. The lastJson
     variable stores the previous response for comparison.

  3. Streaming toggle: pollingEnabled controls whether to fetch from Python;
     streamingEnabled controls whether to forward to the glasses. Both can be
     on independently. For example, pollingEnabled=true + streamingEnabled=false
     means the server stays in sync with Python (deduplication keeps working)
     but pauses the stream to the glasses.

Error Handling
--------------
If Python is not running or not reachable, RestTemplate throws a
RestClientException. This is caught and logged, and the scheduler keeps running.
The system recovers automatically when Python comes back up — no restart needed.

CHAPTER 7 — POOL DETECTOR (pool_detector.py)
================================================================================

What It Does
------------
The weld pool is the molten metal region at the tip of the welding electrode.
Its position, size, and brightness are indicators of weld quality. The pool
detector watches the camera feed from the glasses and finds the weld pool in
each frame using computer vision.

The result — position normalized to 0.0–1.0 in both X and Y — is sent to the
Java server, which forwards it to the glasses. The glasses then draw a circle
on the AR overlay at the correct position.

Detection Pipeline (Step by Step)
-----------------------------------
Each frame goes through this sequence:

  Step 1 — Gaussian Blur
    The raw camera image contains JPEG compression artifacts and fine noise.
    Gaussian blur replaces each pixel with a weighted average of its neighbors,
    smoothing out fine detail. This prevents small noise specks from being
    mistaken for the weld pool.
    Parameter: BLUR_KERNEL (must be an odd number — e.g. 5, 7, 9)

  Step 2 — Brightness Threshold
    After blurring, every pixel brighter than BRIGHTNESS_THRESHOLD is set to
    white; everything else is set to black. The result is a binary image where
    white pixels mark the brightest region (the weld pool or test flashlight).
    Parameter: BRIGHTNESS_THRESHOLD (0–255, typically 180–220 for welding)

  Step 3 — Morphological Opening (Erode → Dilate)
    The binary image may still contain small isolated white specks outside the
    main blob. Opening removes them: erosion shrinks all white regions (small
    specks disappear entirely), then dilation restores the size of the remaining
    large blob.
    Parameter: MORPH_KERNEL (size of the erosion/dilation kernel)

  Step 4 — Morphological Closing (Dilate → Erode)
    Inside the weld pool, uneven brightness or JPEG artifacts can create small
    black holes in the white blob. Closing fills them: dilation expands the blob
    to cover any holes, then erosion restores the outer boundary.

  Step 5 — Find Contours
    OpenCV's findContours() locates the boundaries of all white regions in the
    cleaned binary image. Each boundary is a contour — a list of edge points.

  Step 6 — Area and Circularity Filter
    For each contour:
      - If its area is smaller than MIN_BLOB_AREA, it is noise — skip it.
      - Circularity = 4π × area / perimeter² (equals 1.0 for a perfect circle).
        If circularity < MIN_CIRCULARITY, the shape is not round — skip it.
    Only contours that pass both filters are candidates.
    Parameters: MIN_BLOB_AREA (pixels), MIN_CIRCULARITY (0.0–1.0)

  Step 7 — Select Largest Candidate
    If multiple round blobs pass the filter, the largest by area is selected.
    The assumption: the weld pool is the largest bright circular object in frame.
    Smaller candidates are likely reflections or sparks.

  Step 8 — Normalize and Return
    The center (cx, cy) and radius are normalized to the image dimensions so the
    result is resolution-independent. The glasses can apply the result to any
    screen size.

The Annotated Frame
--------------------
For every processed frame — whether a pool was detected or not — the detector
saves a copy of the frame to the annotated/ folder:
  - Pool detected: green circle at the pool boundary + red dot at the center
  - No pool:       raw color frame, unchanged

This is critical for video recording. The Java server's FrameWebSocketHandler
stitches all frames in annotated/ into the final MP4 (falling back to raw frames
if annotated/ is empty). If annotated/ had gaps (frames with no detection not
saved), ffmpeg's numbered-sequence input (%05d) would fail at those gaps and
produce a broken or truncated video.

Design Decision: TRACKING_ENABLED removed
------------------------------------------
An earlier version of the code had a module-level TRACKING_ENABLED = True variable
that could be set to False to pause detection. This was never wired up to any
external control — it was a leftover development convenience. The equivalent
function is already handled by the Java server's trackingEnabled flag: when
tracking is disabled, Java accepts the POST from the detector but does not forward
it to the glasses. Having an unreachable dead variable in Python was misleading.
It was removed.

Settings Refresh from Dashboard
---------------------------------
Every 10 seconds, the detector calls GET /api/settings on the Java server and
updates its threshold/blur/morphology parameters. This means an operator can tune
the detector live from the dashboard while a session is running, without restarting
the Python script. The Java server stores these settings in ServerState.

Testing without a Welder
-------------------------
test_pipeline.py generates synthetic frames: a bright circular blob moving in a
sine arc against a dark background. This simulates what the detector sees (the
bright weld pool or flashlight) without needing physical hardware. It is used to:
  - Confirm the detection pipeline works after changing parameters
  - Verify that annotated/ frames are saved for all 60 test frames
  - Stitch a test video via ffmpeg and confirm the output is playable

CHAPTER 8 — WEBSOCKET FRAME HANDLER (FrameWebSocketHandler.java)
================================================================================

What It Does
------------
When the camera feature is enabled, the glasses send their camera feed to the
server as a stream of individual JPEG images over a WebSocket connection. Each
incoming frame is a binary message — raw bytes representing one JPEG image.

The handler saves each frame to disk with a sequential filename
(frame_00000.jpg, frame_00001.jpg, ...) in the frames/ folder. The pool detector
(pool_detector.py) monitors this folder and processes new frames as they arrive.

Why WebSocket for Frames?
--------------------------
Camera frames are binary data — not text, not JSON. WebSocket is designed for
exactly this: a persistent bidirectional channel that efficiently carries both
text and binary data. HTTP would require a new connection for every frame, which
has significant overhead at 30fps. WebSocket keeps one connection open and the
glasses push frames through it continuously.

The cameraEnabled Gate
-----------------------
Frames are only saved when serverState.isCameraEnabled() is true. When camera
capture is disabled from the dashboard, the server immediately sends a
"cameraControl" SSE event to the glasses telling them to stop their camera. The
cameraEnabled check in the frame handler is a fallback: if frames arrive anyway
(e.g. the command was delayed), they are silently discarded instead of filling
up the disk.

Wi-Fi Hiccup Handling — The 5-Second Delay
-------------------------------------------
When the glasses disconnect from the WebSocket, the first instinct would be to
immediately stitch the frames into a video. But Wi-Fi connections drop and
re-establish frequently, especially at the short distances used in a workshop.
Stitching immediately on every hiccup would produce many short, broken videos
instead of one continuous session recording.

The solution: a 5-second timer. On disconnect, a delayed task is scheduled to
run stitchAndClean() after 5 seconds. If the glasses reconnect within those 5
seconds, the timer is cancelled and the session continues seamlessly — frames
keep their sequential numbers and nothing is lost.

Only if the glasses stay disconnected for the full 5 seconds does the video
get stitched. This tolerates brief Wi-Fi drops without fragmenting the recording.

Annotated vs Raw Frames for Stitching
--------------------------------------
After stitching, the code checks whether annotated/ contains any frames. If it
does, those are used for the video instead of the raw frames. This means the
final recording shows the detection circles drawn by pool_detector.py, making
it possible to review where the weld pool was tracked throughout the session.

If the pool detector was not running (annotated/ is empty), the raw frames are
used — the video is still produced, just without detection overlays.

Buffer Size
-----------
The default Spring WebSocket buffer is too small for JPEG images. WebSocketConfig
raises the buffer to 512 KB. A JPEG frame from the BT-300 camera at typical
quality settings is well under 512 KB, so this gives comfortable headroom.

CHAPTER 9 — DASHBOARD (DashboardController.java + dashboard.html)
================================================================================

What the Dashboard Does
-----------------------
The dashboard is a single web page at http://localhost:9999/dashboard. It gives
the operator full control over the server without writing any code or restarting
anything. All changes take effect immediately.

The page auto-refreshes its status every 2 seconds using JavaScript fetch() calls
to the /api/status endpoint. This keeps all status indicators current without
the operator having to manually refresh.

Page Structure
--------------
  Overview page
    - Status indicators: Python AI reachable, polling active, streaming active
    - Live data card: current (A), voltage (V), gas flow (l/min), last update time
    - Start/Stop Session button: enables/disables both polling and streaming together
    - Last pool detection result

  Glasses Preview page
    - Faithful recreation of the Android HUD: gauges + porosity heatbar
    - Uses live data when a session is active, simulated data otherwise

  Camera & Detection page (developer-only)
    - Camera toggle (disabled by default, with a notice explaining it is a POC)
    - Pool tracking toggle
    - Frame counter and WebSocket connection status
    - Recorded video list with playback

  Camera Settings page (developer-only, was: Server Settings)
    - Detection parameters: brightness threshold, blur kernel, morph kernel,
      min blob area, min circularity
    - Frame capture rate (fps for the stitched MP4)
    - Saved immediately to ServerState; pool_detector.py picks them up within 10s

  App Settings page (developer-only)
    - Gauge display ranges (voltage, amperage, gas flow min/max)
    - Heatbar duration: seconds of porosity history shown on glasses
    - Overlay opacity and pool detection overlay toggle
    - The Android app fetches these on launch; restart the app to apply changes

  API Endpoints page
    - Reference list of all server endpoints, grouped by category:
      Core (stream, pool POST, frame count),
      Configuration (settings, app-settings, status),
      Camera & Detection (camera toggle, video list, video streaming)

User Profile vs Developer Profile
----------------------------------
The dashboard supports two operator profiles, switchable from the user-chip in
the bottom-left corner of the sidebar:

  User profile (default)
    - Sees only Overview and Glasses Preview
    - Intended for the welder or a non-technical session operator who only
      needs to start a session and watch the live feedback

  Developer profile
    - Sees everything: Overview, Glasses Preview, Camera & Detection,
      Camera Settings, and App Settings
    - Intended for the engineer tuning the system or developing new features

Clicking the user-chip toggles between the two roles. The choice is persisted
in localStorage under "ar-role" so it sticks across reloads. If the operator
switches to User profile while sitting on a developer-only page, the dashboard
automatically jumps to Overview so they are not stranded on a hidden page.

The role state is held in a single HTML attribute (data-role on the <html>
element) and developer-only sections/items are tagged with data-dev-only.
A single CSS rule hides them when data-role="user" — no per-component
conditionals needed.

Design Decision: Camera as Background POC
------------------------------------------
The camera capture feature — sending frames from the glasses to the server for
recording — is a proof-of-concept. It requires a stable Wi-Fi connection, adds
load to the glasses, and is not central to the core use case (displaying AI data).
For these reasons it was intentionally separated from the main session flow:

  - cameraEnabled starts as false (must be explicitly enabled)
  - Camera controls live on a separate dashboard page
  - The "Start Session" button only toggles polling and streaming, not the camera
  - The dashboard shows a notice on the camera page explaining it is a POC

This separation means the core welding feedback system works without any camera
involvement. The camera is an optional add-on that can be enabled when needed.

Design Decision: Remove Alert Thresholds
-----------------------------------------
An early design included configurable alert thresholds (e.g. alert when voltage
drops below X). These were removed because:
  - The AR glasses are a guidance display, not an alarm system
  - The welder is expected to monitor parameters continuously, not wait for alerts
  - Alerts added complexity to the UI without clear benefit for the thesis scope
  - If needed in future, they can be re-added without touching the rest of the code

Design Decision: Remove Wire Speed, Add Gas Flow
-------------------------------------------------
The original dashboard referred to "wire speed" as one of the welding parameters.
The actual sensor channel is shielding gas flow (liters per minute). Shielding
gas flow is a critical MIG/MAG welding parameter — too low causes porosity (gas
bubbles in the weld), too high wastes gas. The field was renamed to gasFlow across
the entire codebase.

Design Decision: Inline Video Playback
----------------------------------------
Previously, clicking a recorded video's filename in the dashboard did nothing.
A GET /api/video/{filename} endpoint was added that serves the MP4 file inline
with the Content-Disposition: inline header. The browser plays the video in a new
tab without downloading it. Filename validation (rejecting ".." and path
separators) prevents directory traversal attacks.

Design Decision: Separate pollingEnabled from streamingEnabled
--------------------------------------------------------------
Both flags exist so the operator has fine-grained control:
  - pollingEnabled=true, streamingEnabled=false: the server stays in sync with
    Python (deduplication history is current) but pauses the stream. Useful during
    a setup phase where you want the server running but not broadcasting yet.
  - Both true: normal operation.
  - Both false: server is idle. The "Start Session" button sets both together for
    the normal case.

CHAPTER 10 — DNS AND NETWORK (DnsConfig.java, WebSocketConfig.java)
================================================================================

mDNS Registration
-----------------
On startup, DnsConfig registers the server as "sse-server" on the local network
using mDNS (multicast DNS, Apple calls this Bonjour). The registration announces:
  - Service type: _http._tcp.local. (a standard HTTP service)
  - Name: sse-server
  - Port: 9999
  - Path: /stream

From this point on, any device on the same Wi-Fi network can reach the server at
sse-server.local:9999 regardless of the current IP address of the laptop.

The Android app is configured to connect to sse-server.local:9999/stream. Because
the name is fixed, sessions are reproducible — no configuration changes needed
between sessions even if the laptop gets a new IP from the router.

Windows Firewall Note
---------------------
Windows Firewall may block the mDNS UDP traffic (port 5353) by default. The
one-time fix: allow inbound UDP port 5353 in the Windows Defender Firewall advanced
settings, or run the server as Administrator the first time to trigger the firewall
prompt.

WebSocket Buffer
----------------
WebSocketConfig registers FrameWebSocketHandler on the /frames path and raises
the binary message buffer to 512 KB. The glasses encode camera frames as JPEG
before sending — JPEG compresses well, but a full-resolution frame at typical
quality settings can still exceed Spring's default buffer size. 512 KB gives
enough headroom while staying well below memory limits.

CHAPTER 11 — CAMERA FEATURE OVERVIEW (Proof of Concept)
================================================================================

End-to-End Flow
---------------
  1. Operator enables camera on dashboard → POST /api/toggle/camera
  2. Java broadcasts "cameraControl" SSE event: {"enabled": true}
  3. Glasses receive the event, start their Camera2 API capture, open WebSocket
     to ws://sse-server.local:9999/frames
  4. Glasses send JPEG frames as binary WebSocket messages (typically 15–30 fps)
  5. FrameWebSocketHandler saves each frame: frames/frame_00000.jpg, etc.
  6. pool_detector.py detects the new frame, processes it, saves annotated copy
     to annotated/, POSTs result to /pool
  7. Java receives POST /pool, broadcasts "pooldetection" SSE event to glasses
  8. Glasses draw the detection circle at the returned coordinates on the overlay

  On session end:
  9. Operator disables camera → POST /api/toggle/camera
  10. "cameraControl" {"enabled": false} sent to glasses
  11. Glasses stop camera, close WebSocket
  12. After 5-second timeout (hiccup grace period), server stitches frames → MP4
  13. Video available at GET /api/video/{filename} and listed in dashboard

Why This is a POC
-----------------
The camera feature works end-to-end but has limitations that would need to be
addressed before production use:

  - The glasses BT-300 run Android 5.1, which limits Camera2 API capabilities
  - Wi-Fi bandwidth may not be sufficient for reliable 30fps streaming in a
    real workshop environment (interference, distance, obstacles)
  - The pool detector is a brightness-based blob detector optimized for testing
    with a flashlight — a real weld arc is much brighter and the camera may need
    an IR filter or ND filter to get a usable image
  - The detection circles are drawn on the AR overlay based on the server-reported
    position, but there is latency (camera → server → processing → result → glasses)
    which means the circle position lags behind the real pool position

CHAPTER 12 — FULL DESIGN DECISIONS LOG
================================================================================

This chapter documents every significant decision made during development,
with the reasoning at the time.

[D-01] SSE over WebSocket for the main data channel
  Decision: Use SSE (one-way) rather than WebSocket (two-way) for the main data
            stream from server to glasses.
  Reason:   The glasses only need to receive data, never send it on this channel.
            SSE is simpler (plain HTTP, no upgrade), auto-reconnects on drop, and
            has native Android support. WebSocket was reserved for the binary
            camera feed because SSE cannot carry binary data client→server.

[D-02] Single SSE connection with named events instead of multiple endpoints
  Decision: All events (welddata, pooldetection, cameraControl) travel on the
            same /stream endpoint with different event names.
  Reason:   Managing multiple connections from the glasses adds complexity and
            doubles the number of connection-state issues. Named events on a
            single connection achieve the same clean separation. Android's
            EventSource API supports per-name listeners.

[D-03] pollingEnabled and streamingEnabled as separate toggles
  Decision: Keep them as independent flags rather than merging into one.
  Reason:   Allows the operator to fetch and deduplicate data from Python without
            immediately broadcasting. Useful for setup phases and debugging.
            The "Start Session" button handles the common case (both together).

[D-04] cameraEnabled decoupled from streamingEnabled
  Decision: Add a third independent flag cameraEnabled for camera capture.
  Reason:   The camera is a proof-of-concept feature that should not interfere
            with the main welding feedback flow. Disabling streaming should not
            stop the camera from recording, and disabling the camera should not
            stop streaming. Each flag controls exactly one concern.

[D-05] Camera disabled by default
  Decision: cameraEnabled starts as false on every server start.
  Reason:   Camera capture consumes bandwidth, battery on the glasses, and disk
            space on the server. It should be an intentional choice by the
            operator, not an accidental default.

[D-06] 5-second stitch delay for Wi-Fi hiccups
  Decision: After glasses disconnect from WebSocket, wait 5 seconds before
            stitching the video. Cancel the stitch if they reconnect in time.
  Reason:   Wi-Fi connections drop briefly in workshop environments. Stitching
            immediately would fragment a continuous session into many short clips.
            5 seconds was chosen as long enough to cover most reconnections but
            short enough that the operator does not wait long after a real end.

[D-07] Always save to annotated/ even when no pool detected
  Decision: pool_detector.py saves the raw (unannotated) frame to annotated/
            at every early return, not just when a pool is found.
  Reason:   ffmpeg uses a sequential numbered pattern (frame_%05d.jpg) to stitch
            video. If frames are missing from the sequence (only detected frames
            were saved), ffmpeg treats the gap as end-of-sequence and truncates
            the video. Every frame must be present in annotated/ to produce a
            complete recording.

[D-08] TRACKING_ENABLED dead variable removed from pool_detector.py
  Decision: Remove the module-level TRACKING_ENABLED = True variable.
  Reason:   It was never set to False from any external control — it was a
            development remnant. The equivalent function is served by Java's
            trackingEnabled flag, which actually controls whether detection
            results are forwarded to the glasses. The Python variable was
            misleading without serving any purpose.

[D-09] lastDataPacket initialized to "" not null
  Decision: private volatile String lastDataPacket = "";
  Reason:   Java's Map.of() throws NullPointerException on null values. When
            lastDataPacket was null (before the first poll), every /api/status
            call returned HTTP 500. This silently broke the dashboard toggle
            buttons because the JavaScript never received a valid JSON response.
            Empty string is a safe initial value — the dashboard JavaScript
            guards with `if (!raw) return;`.

[D-10] Alert thresholds removed entirely
  Decision: Do not implement configurable alert thresholds for voltage, amperage,
            and gas flow.
  Reason:   The system is a guidance overlay, not an alarm system. The welder
            monitors parameters continuously. Alert thresholds added UI complexity
            and settings fields without clear benefit for the thesis scope.
            This can be added in future work without changing the existing code.

[D-11] Ghost connections: remove count, keep heartbeat
  Decision: Remove the numeric "X clients connected" count from the dashboard;
            keep the heartbeat mechanism and the green dot indicator.
  Reason:   The count was confusing because ghost connections inflated it (a
            dropped connection might still show as 1 or 2 after reconnect). The
            green dot (≥1 connection) is sufficient for the operator to know
            whether the glasses are connected. The heartbeat still clears dead
            connections so the count used internally stays accurate.

[D-12] Wire speed renamed to gas flow
  Decision: Rename wireSpeed to gasFlow throughout the codebase.
  Reason:   The actual sensor channel being read is shielding gas flow
            (liters/minute), not wire feed speed. Gas flow is critical for
            weld quality (porosity prevention) and should be named correctly.

[D-13] Inline video playback via /api/video/{filename}
  Decision: Serve recorded MP4 files inline via the server rather than linking
            to local file paths.
  Reason:   A local file path (file://C:/...) would only work on the same machine
            running the server. Serving via HTTP (/api/video/{filename}) works
            from any machine on the network. The Content-Disposition: inline
            header tells the browser to play the video rather than download it.
            Path traversal protection (rejecting ".." in the filename) prevents
            the endpoint from being used to serve arbitrary files.

[D-14] mDNS for network discovery instead of hardcoded IP
  Decision: Use JmDNS to register the server as sse-server.local.
  Reason:   DHCP means the server's IP address changes between sessions. Any
            hardcoded IP in the Android app would break every time. mDNS
            resolves the current IP automatically on the local network, making
            the system self-configuring after the one-time firewall setup.

[D-15] Dashboard settings changes picked up by pool_detector.py via polling
  Decision: pool_detector.py re-fetches /api/settings every 10 seconds rather
            than the dashboard pushing changes to it.
  Reason:   Push would require the Java server to maintain a reference to the
            Python process or an outgoing HTTP connection. Polling keeps the
            architecture simple: Java is always the server, Python is always
            a client. 10 seconds is short enough to be responsive during
            tuning sessions.

CHAPTER 13 — HOW TO RUN THE SYSTEM
================================================================================

Prerequisites
-------------
  - Java 17 or higher
  - Python 3.9 or higher with: opencv-python, numpy, requests
  - ffmpeg installed (winget install ffmpeg on Windows)
  - Epson Moverio BT-300 with the companion Android app installed
  - Server and glasses on the same Wi-Fi network

Starting a Session
------------------
  1. Start the Java server:
       ./mvnw spring-boot:run   (or run ThesisRemyApplication from IDE)

  2. Start the Python AI program (external — not part of this codebase):
       Ensure it is running at http://127.0.0.1:8060/api/v1/live

  3. Start the pool detector (optional, for camera feature):
       python pool_detector.py

  4. Open the dashboard in a browser:
       http://localhost:9999/dashboard

  5. On the dashboard Overview page, click "Start Session" to enable polling
     and streaming.

  6. Connect the glasses by starting the AR app. It connects to
     sse-server.local:9999/stream automatically via mDNS.

  7. If using the camera feature:
       - Go to the Camera & Detection page on the dashboard
       - Enable Camera (note: this is a proof-of-concept feature)
       - Enable Pool Tracking

  8. To end the session: click "Stop Session" on the dashboard.
     If the camera was active, the video will be stitched automatically
     and appear in the Recordings list after a few seconds.

Troubleshooting
---------------
  - Python AI not reachable: check that the Python AI is running at port 8060.
    The dashboard status panel shows a red indicator if it cannot be reached.

  - Glasses not connecting: check that the server machine's firewall allows
    inbound TCP on port 9999 and inbound UDP on port 5353 (mDNS).

  - Pool detector not detecting: lower BRIGHTNESS_THRESHOLD in the Camera Settings
    panel if nothing is detected, or enable DEBUG_MODE in pool_detector.py to
    see the binary mask. For testing without a welder, use a flashlight.

  - Video not stitching: check that ffmpeg is installed and accessible. Run
    `ffmpeg -version` in a terminal to confirm. The server console log shows
    whether stitching succeeded or failed.
